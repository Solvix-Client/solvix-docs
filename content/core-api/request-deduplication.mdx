---
title: Request Deduplication
description: Automatically deduplicate identical in-flight requests. 1000 concurrent calls → 1 network request.
---

When `dedupe` is enabled, Solvix prevents redundant network calls. If a request with the same method, URL, body, and headers is already in-flight, subsequent calls share the same Promise — the result is broadcast to all callers.

> **The classic "1000 concurrent identical requests → 1 actual network call" feature.**

## Basic Usage

```ts
import { createClient } from "@adityadev13/solvix";

const client = createClient({
  baseURL: "https://api.example.com",
  dedupe: true,
});
```

Now 100 concurrent calls to the same endpoint:

```ts
const results = await Promise.all(
  Array.from({ length: 100 }, () => client.get("/data"))
);

// Results contains 100 identical responses
// Network: 1 request was actually sent
```

## How It Works

Solvix generates a **SHA-256 fingerprint** of the request (method, URL, body, headers). In-flight requests are stored in a map keyed by this fingerprint:

```
Request A: GET /users → fingerprint("GET|/users||") → store Promise
Request B: GET /users → fingerprint("GET|/users||") → return same Promise
Request C: GET /users → fingerprint("GET|/users||") → return same Promise

Response received → resolve all 3 promises → 1 network call total
```

SHA-256 is **only computed when `dedupe` or `cache` is enabled** — no performance impact when disabled.

## Cache Integration

Dedup works before the cache check:

```
Dedup Check ──→ Hit? → return in-flight Promise
   ↓ Miss
Cache Check ──→ Hit? → return cached response
   ↓ Miss
Network Request → store in cache → return response
```

This means a request that was just completed (cached) won't trigger a new network call even if another request comes in before the cache TTL expires.

## Dedup + Retry

Deduplicated requests share the same retry lifecycle:

```ts
const client = createClient({
  dedupe: true,
  retry: { retries: 3 },
});

// 100 concurrent calls → 1 network call with 3 retries max
// All 100 get the same result
```

## Dedup + Token Refresh

When token refresh is configured, dedup also applies to the refresh operation itself — the classic "100 concurrent 401s → 1 token refresh" pattern:

```ts
const client = createClient({
  dedupe: true,
  auth: {
    refreshToken: async () => {
      // This runs only once even if 100 requests get 401
      const res = await fetch("/auth/refresh");
      return (await res.json()).token;
    },
  },
});
```

## Per-Request Exclusion

To skip dedup for a specific request:

```ts
// This request won't be deduped (useful for non-idempotent mutations)
await client.post("/analytics", eventData, { dedupe: false });
```

## Fingerprint Customization

Use `fingerprint` to customize the dedup key:

```ts
const client = createClient({
  dedupe: true,
  fingerprint: {
    // Only method + URL (ignore body and headers)
    includeBody: false,
    includeHeaders: false,
  },
});
// GET /users → same key regardless of headers
```

## Memory Safety

The in-flight registry evicts entries FIFO at 10,000 to prevent memory leaks in long-running processes.

## Performance Impact

| Scenario | Requests | Network Calls | Saved |
|----------|----------|---------------|-------|
| 1000 users load dashboard | 1000 | **1** | 99.9% |
| Retry storm | 500 | **~3** (1 per retry) | 99.4% |
| No dedup | 100 | 100 | 0% |

## Best Practices

1. **Enable globally for GET requests** — idempotent reads benefit most
2. **Disable for POST/PUT/PATCH** — mutations shouldn't be deduped (unless idempotent)
3. **Combine with retry** — dedup + retry = efficient failure recovery
4. **Monitor dedup hit rate** — a high hit rate means your UI is making too many duplicate calls
