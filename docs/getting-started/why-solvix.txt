<h2 id="the-problem-with-traditional-http-clients">The Problem with Traditional HTTP Clients</h2>
<p>Most HTTP clients focus on one thing: sending requests and receiving responses. Everything else — retries, security, observability, queue management — is left to the developer.</p>
<p><strong>Result:</strong> Production codebases end up with ad-hoc retry wrappers, manual token refresh logic, scattered logging, and inconsistent error handling.</p>

<h2 id="where-solvix-excels">Where Solvix Excels</h2>
<h3 id="1-fully-integrated-pipeline">1. Fully Integrated Pipeline</h3>
<p>In Solvix, every feature plugs into a single request pipeline. Retries interact with the circuit breaker. Rate limiting respects queue priority. Deduplication is aware of caching. Features don't fight each other — they compose.</p>
<h3 id="2-true-observability">2. True Observability</h3>
<p>Solvix doesn't just send requests — it traces them. Every request gets a correlation ID, a W3C traceparent header, a 15-stage timeline, and performance metrics. You can subscribe to lifecycle events globally via <a href="/docs/core-api/logging-events-solvixbus">SolvixBus</a>.</p>
<h3 id="3-enterprise-security-by-default">3. Enterprise Security by Default</h3>
<p>CRLF injection protection, forbidden header stripping, and snapshot redaction are always on. Additional layers (HTTPS enforcement, domain allowlisting, CSRF protection, size guards) are one config field away.</p>
<h3 id="4-no-external-dependencies">4. No External Dependencies</h3>
<p>Solvix has zero runtime dependencies (except <code>undici</code> for proxy/TLS features, which is optional). The entire library is a single, self-contained build.</p>
<h2 id="where-solvix-differs-in-philosophy">Where Solvix Differs in Philosophy</h2>
<ul>
<li><strong>Opt-in, not opt-out</strong> — features are disabled by default. You enable what you need.</li>
<li><strong>Observability-first</strong> — every feature emits events, logs, and metrics automatically.</li>
<li><strong>Middleware over configuration</strong> — complex logic goes into custom middleware, not config bloat.</li>
<li><strong>Transport-agnostic</strong> — swap out the underlying HTTP transport without changing your code.</li>
</ul>
<h2 id="when-to-use-solvix">When to Use Solvix</h2>
<p>Solvix is ideal for:</p>
<ul>
<li>Large-scale frontend applications with complex API needs</li>
<li>Backend services requiring resilience patterns</li>
<li>Multi-runtime projects (Node.js + browser + edge)</li>
<li>Enterprise systems with strict security requirements</li>
<li>Microservices architectures with observability needs</li>
</ul>
<h2 id="when-not-to-use-solvix">When Not to Use Solvix</h2>
