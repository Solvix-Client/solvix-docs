1b:T544f,<p>Solvix supports <strong>Koa-style middleware</strong> — async functions that receive the request context and a <code>next()</code> callback. Middleware can modify the request before it's sent, the response after it's received, or wrap the entire pipeline.</p>
<blockquote>
<p><strong>Interceptors are a good idea, but middleware is better. Middleware composes — interceptors stack linearly.</strong></p>
</blockquote>

<h2 id="how-middleware-works">How Middleware Works</h2>
<p>Middleware follows the <strong>onion model</strong> — code before <code>await next()</code> runs on the way in (before the request), code after runs on the way out (after the response):</p>
<pre><code>Request → [middleware 1] → [middleware 2] → [transport] → [middleware 2] → [middleware 1] → Response
               ↓                ↓                           ↑                  ↑
            pre-req          pre-req                     post-resp         post-resp
</code></pre>

<h2 id="middleware--solvix-features">Middleware + Solvix Features</h2>
<p>Middleware runs <strong>inside</strong> the retry loop, before the transport. This means:</p>
<ul>
<li>Middleware runs on <strong>every retry</strong> attempt</li>
<li>Middleware can modify <code>ctx.url</code> and <code>ctx.options</code> — changes persist across retries</li>
<li>Middleware <strong>cannot</strong> bypass the circuit breaker or rate limiter (they run before the retry loop)</li>
</ul>
<pre><code>Retry Loop:
  → Rate Limit Check
  → Circuit Breaker Check
  → Middleware Stack (user-defined)
  → Transport (fetch/custom)
  → Response/Error → Retry? → back to top
</code></pre>
<h2 id="middleware-order">Middleware Order</h2>
<p>Middleware is executed in the order it was registered:</p>
<figure data-rehype-pretty-code-figure=""><pre style="background-color:#22272e;color:#adbac7" tabindex="0" data-language="ts" data-theme="github-dark-dimmed"><code data-language="ts" data-theme="github-dark-dimmed" style="display: grid;"><span data-line=""><span style="color:#ADBAC7">client.</span><span style="color:#DCBDFB">use</span><span style="color:#ADBAC7">(middleware1); </span><span style="color:#768390">// Runs first (outermost)</span></span>
<span data-line=""><span style="color:#ADBAC7">client.</span><span style="color:#DCBDFB">use</span><span style="color:#ADBAC7">(middleware2); </span><span style="color:#768390">// Runs second</span></span>
<span data-line=""><span style="color:#ADBAC7">client.</span><span style="color:#DCBDFB">use</span><span style="color:#ADBAC7">(middleware3); </span><span style="color:#768390">// Runs third (innermost — closest to transport)</span></span>
<span data-line=""> </span>
<span data-line=""><span style="color:#768390">// When a request flows through:</span></span>
<span data-line=""><span style="color:#768390">// middleware1 → middleware2 → middleware3 → transport → middleware3 → middleware2 → middleware1</span></span></code></pre></figure>

<h2 id="best-practices">Best Practices</h2>
<ol>
<li><strong>Always call <code>await next()</code></strong> — otherwise the request stops at your middleware</li>
<li><strong>Keep middleware focused</strong> — one concern per middleware</li>
<li><strong>Handle errors</strong> — wrap <code>await next()</code> in try/catch for error tracking</li>
<li><strong>Don't mutate <code>ctx.options.group</code></strong> — it's used by the request group system</li>
<li><strong>Test middleware independently</strong> — create a mock context and call your middleware with it</li>
</ol>
