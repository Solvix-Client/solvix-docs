1c:T4ad2,<p>The Token Refresh Orchestrator automatically handles 401 responses by refreshing the auth token and retrying the original request. It's <strong>stampede-safe</strong> — if 100 requests get 401 simultaneously, only one refresh call is made.</p>
<blockquote>
<p><strong>Stop writing token refresh wrappers. Solvix handles the 401 → refresh → retry flow automatically.</strong></p>
</blockquote>

<h2 id="how-it-works">How It Works</h2>
<pre><code>1. Request sent with Authorization header (via attachToken)
2. Response: 401 Unauthorized
3. shouldRefresh(error) → true
4. Check if another request is already refreshing:
   ├── Yes → wait for that refresh to complete
   └── No  → call refreshToken()
5. attachToken(newToken, ctx) — update context headers
6. Retry the original request
7. If refresh fails → propagate error to all waiting requests
</code></pre>

<h2 id="token-refresh--retry-integration">Token Refresh + Retry Integration</h2>
<p>The refresh happens inside the retry loop. If <code>retry</code> is configured, Solvix will:</p>
<ol>
<li>Get 401 → refresh token → retry</li>
<li>If retry also gets 401 → refresh again (up to retry count)</li>
</ol>

<h2 id="best-practices">Best Practices</h2>
<ol>
<li><strong>Always set <code>shouldRefresh</code> for non-401 auth errors</strong> — some APIs use 403 for expired tokens</li>
<li><strong>Handle refresh failure</strong> — redirect to login, clear session, etc.</li>
<li><strong>Use <code>credentials: "include"</code></strong> for refresh endpoints with httpOnly cookies</li>
<li><strong>Combine with <code>retry</code></strong> — allows multiple refresh attempts if the auth server is flaky</li>
<li><strong>Monitor refresh events</strong> — frequent refreshes indicate short-lived tokens or clock drift</li>
</ol>
