1c:T598b,<p>The Retry Engine automatically retries failed requests using configurable strategies. It integrates with the circuit breaker, rate limiter, and deduplication system — retries never overwhelm failing services.</p>
<blockquote>
<p><strong>Don't build retry wrappers. Solvix retries are built-in, composable, and production-tested under 50 concurrent failures.</strong></p>
</blockquote>

<h2 id="how-it-works">How it Works</h2>
<pre><code>Request fails ──→ shouldRetry? ──→ No ──→ Throw error
                       │
                      Yes
                       ↓
         Wait: delay = min(baseDelay * factor^attempt, maxTimeout)
         Apply jitter: delay ± 25%
                       ↓
         Adapt: maxTimeout = max(maxTimeout, actualNetworkTime * 2)
                       ↓
         Retry request (circuit breaker check → queue → transport)
                       ↓
         Success? ──→ Return response
         Fail? ──→ Loop back
</code></pre>

<h2 id="best-practices">Best Practices</h2>
<ol>
<li><strong>3 retries max</strong> — more than 5 is rarely useful and can cause backpressure</li>
<li><strong>Enable jitter</strong> — prevents the thundering herd problem when many clients retry simultaneously</li>
<li><strong>Integrate with circuit breaker</strong> — prevents retries from overwhelming a genuinely dead service</li>
<li><strong>Use <code>shouldRetry</code></strong> — don't retry on 4xx errors (client mistakes won't fix themselves)</li>
<li><strong>Monitor retry counts</strong> — <code>SolvixBus.on("request:retry", ...)</code> to alert on excessive retries</li>
<li><strong>Adaptive timing</strong> — automatically adjusts maxTimeout based on actual network performance</li>
</ol>
